Tagline: Track your expenses. Understand your spending.

1. Project overview

SpendSmart is a personal expense tracking web application for college students and young adults who want to understand their daily spending without connecting a bank account. Users manually record purchases and view their own expense history and monthly category totals. The problem is that small daily purchases can accumulate without people having a clear picture of their spending. The goal is a simple, private record of expenses, not a banking service or financial adviser. The target user is someone with basic web skills who may use either a phone or a computer.

2. Scope and requirements

The minimum viable product (MVP) is registration, login/logout, adding and saving an expense, private expense history and updating a user's name and email. A user can enter an expense description, positive dollar amount, category and purchase date. Categories are Food and Dining, Transportation, Shopping, Entertainment, Housing and Utilities, Education, Health and Fitness, and Other. Monthly totals, transaction count, category breakdown, editing and deleting are secondary enhancements. Filtering, CSV export and budget limits are future possibilities. Bank integrations, transfers, receipt scanning, AI advice, multiple currencies and shared accounts are excluded. USD is the only currency. This keeps the required journey small enough to complete and explain.

4. User stories and acceptance criteria

ID Story Acceptance criterion
US-01 As a new user, I want an account so my expenses are private. Valid registration creates one account; duplicate email is rejected.
US-02 As a returning user, I want to sign in securely. Correct credentials open the dashboard; incorrect credentials do not.
US-03 As a student, I want to record a purchase. Valid details save; negative, blank or invalid inputs are rejected.
US-04 As a user, I want to find previous expenses. Records persist after logout and login and only belong to me.
US-05 As a user, I want to update my account. Valid name/email changes persist; duplicate email is rejected.
US-06 As a user, I want to understand spending. Monthly total equals the sum of my current-month records.
US-07 As a user, I want to correct a mistake. I can edit or delete only my own expense.

US-01 through US-05 define the required first slice. US-06 and US-07 are enhancements. Each story has an observable acceptance criterion rather than relying on subjective claims.

5. Technical architecture and data flow

Proposed stack: HTML and CSS for semantic, responsive pages; Python/FastAPI for routes and server-side validation; Jinja2 templates for rendering HTML; SQLite for persistent relational storage; Uvicorn for local development; GitHub for source and issues; pytest with FastAPI TestClient for automated checks; Chrome DevTools/Lighthouse for browser measurement. Native HTML progress elements can show category proportions without a chart library. These choices reduce external dependencies and fit a small single-server application. FastAPI replaces the earlier proposed Flask stack because the available development environment supports it; verify course-specific stack requirements before adopting it as final.

A browser submits an HTML form over HTTP locally (HTTPS in any public deployment). The server checks the session and CSRF token, validates inputs, determines the owner from the authenticated session, and sends parameterized SQL to SQLite. SQLite persists records. The server queries records by owner and renders an HTML response or redirects to the history page. The browser never directly reads the database. The database file stays on the server and is excluded from Git. A public static research site can host this SPEC separately from the running application.

6. Database design

Table Fields Purpose
users id (PK), name, email (unique), password_hash Identity and account information
expenses id (PK), user_id (FK), description, amount_cents, category, spent_on Private expense records
sessions token (hashed PK), user_id (nullable FK), csrf, expires Server-side login state and form protection

One user can have many expenses; every expense belongs to exactly one user. A foreign key enforces ownership relationships and an owner/date index supports history queries. Store amounts as integer cents, not floating-point numbers, to avoid rounding errors. The date uses ISO format. A database constraint rejects nonpositive amounts; server-side validation also limits length, category, amount and date. Emails are unique and normalized to lowercase.

7. Security and privacy

Passwords are salted and hashed using scrypt, never stored in plaintext. Sessions use random opaque tokens, stored as hashes on the server, and HttpOnly/SameSite cookies. Rotate the session when signing in and delete it on logout. Use Secure cookies and HTTPS when hosted publicly. State-changing requests use CSRF tokens and POST. All protected routes require a valid session; read, edit and delete queries constrain both the expense identifier and the authenticated user ID. Return 404 for another user's expense rather than revealing its existence. Parameterized SQL helps prevent SQL injection; HTML templates escape user input. Responses containing private information should not be cached. The application collects name, email and manually entered expense data only; never request bank credentials, card numbers or account balances. Use invented data in screenshots and testing; do not publish the database, session cookies or passwords. Production improvements include login rate limiting, email verification, reauthentication before sensitive changes, account deletion, backups and deployment security review.

8. Design pattern comparison

A simple alternative is one large script that combines form HTML, SQL queries, validation and business rules for every page. This is quick initially, but duplicates ownership checks and makes testing and maintenance difficult. SpendSmart will use an MVC-inspired separation: models/data access (SQLite schema and database helper), views (Jinja templates and CSS), and controllers (FastAPI route functions). The model remains lightweight rather than adding an ORM or repository layer for a small project. This makes it easier to test a route, change the interface without changing SQL, and reuse security and validation helpers. The trade-off is a few additional files and conventions; the benefit is clearer responsibilities. It is not a strict, fully separated MVC framework.

10. Planned measurement

Measure the dashboard's Largest Contentful Paint (LCP) in Chrome Lighthouse using mobile settings. Target: 2.5 seconds or less under the selected test conditions. Sign in using a synthetic account with ten expenses, run the Lighthouse performance audit three times under the same settings, record the median LCP, browser version and device/emulation settings. Use the result to decide whether to reduce assets or simplify the dashboard. Also inspect Lighthouse accessibility findings; automated results supplement, not replace, the keyboard and phone checks. 11.2 Technical research findings

ChatGPT reviewed the following official technical resources on November 25, 2026, Eastern time, and identified how they inform the proposed design.

  • FastAPI documentation: Its request routing and validation features support the choice of a Python backend for processing expense submissions and account requests.
  • SQLite foreign key documentation: Each expense will reference its owner's account. Foreign key enforcement will be enabled for database connections to maintain valid relationships.
  • OWASP Authorization Cheat Sheet: Access should be denied by default and permissions checked for every protected request. SpendSmart will check expense ownership on the server, including when a record ID is guessed.
  • Chrome Lighthouse documentation: Lighthouse supports performance and accessibility audits. The planned dashboard measurement will use mobile Lighthouse settings, with separate manual keyboard and phone checks.

11.3 Scope and responsibility

The required account and expense journey takes priority over charts and filters. The proposed design stores monetary amounts as integer cents, uses manual entry in US dollars and excludes banking integrations, payment processing and automated financial advice. AI assisted with research, documentation and initial code; I am responsible for reviewing the technical choices, confirming scope and explaining the implementation. The research findings above are AI-assisted summaries, not a claim of independent student review or completed testing.
